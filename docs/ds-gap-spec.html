① 正文链接

结论：DS 已经有这套墨，而且自己给它起了名字。缺的不是设计，是「它在 domain 分区，产品外壳拿不到」。 提案是把已经重复写了两遍的既有模式提升为 core 的命名基元 —— .tcrn-link / .tcrn-link--quiet —— 外加一处基于实测的修正。

依据

DS 的注释自己点了名。Navigation.tsx:3359 写着「Same inline-record-link ink as the Knowledge result anchor」—— 作者在写第二处的时候就知道这是同一套墨，并且记下来了。两处逐字相同： .tcrn-machine-token__link 与 .tcrn-knowledge-search-results__head a。

但两处都带 domain 前缀（tcrn-machine-token / tcrn-knowledge 在 DOMAIN_CLASS_PREFIXES 里），而 AOS 只外链 tcrnCoreComponentCss。跑一遍切分实测：

选择器core（AOS 外链的那份）domain（AOS 不加载）产品能不能用
.tcrn-machine-token__link无有拿不到
.tcrn-knowledge-search-results__head a无有拿不到
.tcrn-work-board__card-link无有拿不到
a.tcrn-relationship-chip无有拿不到
.tcrn-breadcrumb a有无能

再数一次字节：text-decoration-color: …35% 这套记录链接墨，在 core 出现 0 次、在 domain 出现 2 次。 text-decoration: underline 在 core 只有 1 次，就是面包屑那条 hover。 也就是说 AOS 拿到的那份样式表里，一条常驻下划线的链接墨都没有。

与此同时，core 和 AOS 的样式表里都没有任何裸 a 规则。后果现在就能看见：AOS Truncation 里的「下一页」是浏览器默认蓝 —— 和 DS 当初给 .tcrn-knowledge-search-results__head a 写的死因注释一字不差：「previously had no color/decoration at all — bare UA blue for package consumers」。

② Pagination 渲染出空 nav

结论：这不是漏做，是 no-overclaim 家规落在组件上。DS 在两个地方写明了理由。设计要守住那个理由，不是把它拆掉。 而且产品的数据层本身就不支持页码 —— 诚实的形状是「范围读数 + 下一页」，AOS 已经把它做出来了。

依据：DS 自己的两处声明

  • CSS 注释（Navigation.tsx:4792）：「Pagination renders an empty nav today; this readies the row layout for page controls without asserting markup S036 does not ship」—— 行布局先备好，标记不假装存在。
  • 契约行（contract-stories/content/navigation-rows.ts:11）：rule 是「Separates long indexed lists without losing current filter or proof context」，boundary 是「No remote count claim without product data」。空 nav 就是这条 boundary 的执行结果：DS 手上没有产品数据，就不肯渲染「第 1 / 12 页」。

依据：产品数据层把形状钉死了

AOS 的列表操作（packages/kernel/src/operations/work-items.ts）入参 limit + cursor，回参 nextCursor: string | null + total: integer。 没有 offset，也没有 prevCursor。于是：

  • 页码不可实现 —— 无法寻址「第 7 页」。给 Pagination 加 pageCount 只会招来 boundary 明令禁止的那种声明。
  • 「上一页」服务端不可实现 —— 没有反向游标。
  • 范围读数可实现 —— total 是真实的产品数据，正是 boundary 允许的那种。

AOS 已经把诚实的那个做出来了：Truncation({ shown, total, nextHref })，七处调用点， 并且 shown >= total 时返回 null —— 注释写的是「Never a silent ceiling」。 提案就是把这个被产品验证过的形状收进 DS，计数由消费方供给。

③ 七个工作状态对四种徽章外观

结论：DS 已经答过这题，而且答案是形状，不是数量。它用十一个状态对四种色调， 且收敛只发生在视觉层。真正的缺陷不是「四种不够」，是 AOS 现在的分配跟 DS 的语义反着。

依据：DS 的既有先例

@tcrn/ui-copy-state 里 ReadinessState 是十一个值的封闭联合， presentations 表把它们映到四种色调：positive 1 个、neutral 6 个、warning 3 个、danger 1 个。 分布本来就不均匀。关键在这几点：

  • 收敛只在视觉层。StatusBadge 把 data-state={presentation.state} 落在元素上 （Feedback.tsx:61）—— 色调塌成四种，状态身份仍然一对一、机器可读。色调编码的是紧迫类别，不是身份。
  • 唯一映射表。一张 Record<ReadinessState, CopyStateContract>，不是散在各调用点。
  • fail-closed。normalizeState() 遇到不认识的值落到 unknown → neutral。
  • 不许渲染裸枚举。rawEnumLabelsAllowed: false，sanitizeCopyStateLabel() 会把 形如 pending_acceptance 的字符串挡掉，每个状态都有五语手写文案。

缺陷在分配

AOS 今天的映射（apps/web/src/ui-kit.tsx 的 tone() 与 badgeTone()，两处各写一遍）：done→positive、active→warning、 blocked→danger，其余全 neutral。对着 DS 的语义看，这是反的：

  • active 拿到 warning —— 一个正常推进中的任务被打扮成需要注意。一个健康的迭代看起来像告警板。
  • pending_acceptance 拿到 neutral —— 唯一真的在等人动手的状态，被画成惰性的。

DS 表里的规则是可读的：review_required → warning，ready → positive。 warning 的意思是「有人欠一个动作」，不是「这里在动」。按这条重排：

提案分配：ready/done → positive，pending_acceptance → warning， blocked → danger，planned/active/cancelled → neutral。 计 positive 2、neutral 3、warning 1、danger 1。

映射表放哪

建议留在 AOS，但采用 DS 的形状。理由是方向：那七个词是产品自己的词汇 （search-inbox.ts:532「The seven words for state, from 0002」），而 DS 的 ReadinessState 说的是证据就绪度 —— 另一根轴。把产品状态塞进 DS 会让 DS 背上产品词汇， 正是 domain 分区（DOMAIN_CLASS_PREFIXES 里的 tcrn-work）存在的意义所要避免的。

AOS 要照搬的是形状，不是位置：一张封闭联合 + 单一映射表 + fail-closed 默认 + data-state 保留身份 + 色调派生而非各调用点手写。眼下 tone() 和 badgeTone() 是同一份知识的两份抄写，这本身就是要修的。

附带的小问题，一并请裁。AOS 现在的 STATUS_LABEL 是英文近枚举词 （planned、pending acceptance…），而界面其余部分是中文（「显示 50 条，共 137 条」）。 它之所以没被 DS 的 findRawEnumLabelHits 拦下，只是因为下划线换成了空格。上面的提案样件里我 直接给了一套中文标签（已计划/就绪/进行中/已阻塞/待验收/已完成/已取消）。这是第四个决定，你可以单独否掉它 而保留色调重排。

④ 状态徽章一行放不下就崩

结论：这是 DS 的缺陷，三处叠加，不是一处。它由 Owner 审本稿时指出。 修法是给状态徽章一条硬规则 —— 占一行，永不撑高所在的行 —— 装不下就截断，全文留在 title 里。

依据：三处叠加

成因core 里的声明单行时一折行
会折white-space:normal + overflow-wrap:anywhere，配 width:max-content / max-width:100%无所谓单元格一窄就必折
点悬空::before 定在 inset-block-start:50%恰是文字中心50% 落在两行之间，点不属于任何一行
散排text-align:center无作用变成居中散排

实测：状态列 150px，徽章被 max-width:100% 卡到 126px 时， pending acceptance 撑到 36px 高，而同列其它徽章 24px —— 该行从 48px 涨到 62px（+29%），而同表其它行仍是 48px —— 表格的行高不再是常量。

但根因在案③：撑破它的那个标签本来就不该出现

把七个状态 × 五种语言的 DS 文案逐个量一遍，最宽的是法语 En recette， 85px；而今天渲染的裸枚举 pending acceptance 是 142px —— 宽出 67%。 用 DS 自己的文案，126px 的格子里没有一个状态会折行。折行是渲染裸枚举的后果， 而那本来就被 rawEnumLabelsAllowed: false 禁着。

样件：改前

样件：改后

同样的标签、同样 150px 的列。一行、24px，与同列其它徽章齐平，行高回到常量；放不下的部分交给省略号，全文留在 title 与无障碍名里。

提案

默认值应当归状态片：padding 与圆点的令牌本来就叫 --tcrn-state-chip-padding 与 --tcrn-state-dot-size —— DS 自己早把 Badge 当状态片命名了。长度不可控的那份活（标签名、用户起的名字） 显式 opt-in 到 .tcrn-badge--wrap。Badge 今天一件干两份活，这是分开的时机。

要你裁的第五件。截断 vs 折行，我选截断，理由不是好看：表格的行高是网格的一部分， 折行毁掉网格，截断只毁掉那一格里能读到多少字 —— 后者可恢复（title、悬停、无障碍名都留着全文），前者不可。 如果你认为状态宁可折行也要看全，这条改起来只是一个默认值。

附：查证时撞见的一个 DS 缺陷（不在本次三条内）

core/domain 切分只检查顶层块的选择器，嵌套 at-rule 内部的选择器不看。实测： .tcrn-work-item-row 作为选择器（不是注释）出现在 core 里，位置是 @container tcrn-work-row (max-width: 464px) 内部。tcrn-work 是 domain 前缀， 这一条本该在 domain。

更要紧的是切分自带的那道门（component-css-partition.test.tsx:45 的 leaked 检查）用的是同一个顶层解析器，所以它对这类泄漏是盲的 —— 门是绿的，泄漏是真的。 这跟本次三条无关，我没有动它；按平台规矩这应该是一条独立 Incident，不是顺手改掉的东西。
